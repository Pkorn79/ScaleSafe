# Intake and scope

## Use context before questions

Inspect supplied files, existing pages, brand assets, and prior messages before asking anything. Do not ask the user to repeat information already available.

When information is missing, ask one question at a time in this order:

1. What is the site for, and what should a visitor do?
2. Who is the primary visitor?
3. What business, offer, product, person, or event must be unmistakable in the first viewport?
4. Which existing brand assets, copy, examples, or reference sites should guide the build?
5. Which pages or sections are essential now?
6. Where should forms, purchases, bookings, requests, and downloads go?
7. Where should the site be hosted?

Skip questions whose answers are obvious or immaterial. If the user wants a quick build, recommend a narrow default and proceed.

Each turn may request only one missing fact. Do not combine related requests such as service area and contact method, or audience and offer. Choose the fact that changes the next build decision most; ask for the next fact later only if it remains necessary.

## Scope rules

- Define one primary conversion. Secondary actions must not compete with it.
- Separate launch requirements from later ideas.
- Prefer a complete one-page site over an incomplete multi-page site.
- Add privacy, terms, accessibility, security, or regulated-industry content only when required or supplied; do not invent legal promises.
- Treat forms, payments, authentication, user data, and analytics as integrations with privacy and operational consequences.

## Existing-site edits

Before changing an existing site, identify:

- framework and build commands;
- shared layout, navigation, footer, and design tokens;
- current hosting and redirects;
- affected routes and public assets;
- dirty worktree changes;
- likely regression surface.

Keep edits scoped. Reuse local patterns unless they prevent the requested outcome.
